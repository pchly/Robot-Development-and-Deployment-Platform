# 运行验收报告

运行验收报告把“看起来运行过”收敛为可追溯的工程结论。它属于部署记录，不是新的Runtime，也不改变端侧控制链路。

## 生成时机

- Deployment进入`stopped`或`failed`终态时，由Platform API生成报告；
- 相同DeploymentPlan重新运行时递增`attempt`，历史报告不覆盖；
- 报告、运行次数和低频事件时间线写入SQLite；
- 高频运行指标和最近预览仍是易失数据，不写入SQLite。

## 当前判定规则

| 检查项 | 通过 | 告警 | 未通过 |
|---|---|---|---|
| 运行终态 | `stopped` | — | `failed` |
| 控制频率 | 达到配置值的90% | 75%至90% | 低于75% |
| 控制周期P95 | 不超过单帧预算 | 不超过1.5倍预算 | 超过1.5倍预算 |
| 控制超期比例 | 不超过5% | 5%至20% | 超过20% |
| 执行器故障 | 0 | — | 大于0 |
| 运动命令接收率 | 不低于98% | 90%至98% | 低于90% |
| 执行器安全停止 | 确认进入安全停止 | 缺少证据 | 明确未安全停止 |
| 预览帧龄 | 不超过500 ms | 超过500 ms | 不直接判定控制失败 |

没有产生运动命令时，该项标记为“未触发”，不会把没有识别到目标误判为系统故障。缺少关键端侧指标时报告标记为“证据不足”或“有告警”，不能冒充通过。

## 结论语义

- `通过`：没有失败项或告警项，并具有端侧指标证据；
- `有告警`：功能运行结束，但性能或证据需要复核；
- `未通过`：存在明确失败项；
- `证据不足`：运行结束但没有足够端侧指标形成工程结论。

Studio默认只显示结论、运行次数和摘要。分项实测值、阈值及事件时间线按需展开，避免运行卡片被诊断信息淹没。

## 证据与回放边界

当前持久化的是不可变DeploymentPlan、项目修订来源、每次运行的终态报告和低频事件时间线。控制面不保存原始摄像头视频、逐帧检测结果或高频关节状态，原因是这些数据量大、包含隐私，并且不应反压控制回路。

下一阶段的回放应先基于事件时间线和关键指标快照实现“状态回放”；如确有诊断价值，再由端侧按策略保存有限关键帧或运行包，并以受控制品方式上传。原始全量视频录制不是默认能力。

## 手工验收

1. 启动一条已通过预检的工作流；
2. 观察Runtime进入`running`并产生指标；
3. 正常停止Runtime；
4. 在运行卡片确认出现验收结论；
5. 展开验收证据，核对实测值、要求和说明；
6. 展开运行时间线，确认提交、启动、运行、停止请求和终态顺序；
7. 重启Platform API，确认报告和时间线仍存在；
8. 重新提交同一计划，确认运行次数递增且上一份报告保留。
